# M8: parsed demo summaries, local caching and indexed seek

**Status:** Implemented on `master`.
**Scope:** OPFS/IndexedDB caching, a full demo scan with per-game player,
event, health/armor, stance and damage-attribution data, exact kills/deaths and
vitals at any seek target, a playback-speed slider, and a keyframe index for
fast seeks.

## Demo summary

`JKA_DemoInfo` now scans the whole demo and builds `JKA_DemoSummaryJson`:

- Map name and per-game start/end/level times.
- Player records (slot, name, team, kills, deaths, first/last seen).
- Every obituary event with its server time, target, attacker and means of
  death.
- A per-game health/armor timeline. Base JKA snapshots do not carry remote
  health, so the scan uses every source that does: the team overlay `tinfo`
  server command (teammates' exact health and armor), the duel health
  configstrings (health only), the recorded client's own playerState, and the
  `EV_PAIN` damage event, whose `eventParm` is the health left on the target.
  Deaths set the target to 0/0 and a respawn (dead/alive transition, spawn-in
  effect or a positive sample after a death) starts a new life at the 100/25
  spawn defaults. A health drop in an `EV_PAIN`-only sample is treated as the
  armor being used up, because base armor absorbs all damage until it is empty.
  A one-point drop while health or armor is above 100 is the engine's one-per-
  second over-max decay, not damage.
  Players the demo never samples keep the 100/25 defaults.
- A per-game saber-stance timeline. `BG_PlayerStateToEntityState` mirrors
  `playerState.fd.saberAnimLevel` into `entityState.fireflag` for every player,
  so the scan can record a remote player's stance. The wire field is two bits,
  so it carries none/fast/medium/strong; dual and staff arrive truncated to
  their low two bits. The TypeScript HUD prefers the followed player's live
  cgame stance (patch `0012` corrects dual/staff from the clientinfo saber
  type) and falls back to this timeline; the HP/AP bars come from the scanned
  vitals when the snapshot itself has no remote values.
- A per-game damage timeline. Health/armor losses are recorded with the attacker
  when the demo identifies one: `EV_SABER_HIT` carries victim and attacker,
  `EV_MISSILE_HIT` carries the hit entity and the missile owner, the recorded
  client's `PERS_ATTACKER` gives exact incoming attribution and
  `PERS_ATTACKEE_ARMOR`/`PERS_HITS` identify its hitscan targets, and an
  obituary credits the killing blow. Hitscan damage outside those paths, force
  damage and world damage stay with attacker `-1`. The scan resets the damage
  list per game.
- Players who disconnect are marked `left`; if the same name returns, the
  record is reactivated and flagged `returned`. Records that left and never came
  back are shown greyed out with a **left** badge.
- A new gamestate starts a new game section, so map loads/restarts appear as
  separate games (`jka_demoGamestates` is incremented in `CL_ParseGamestate`).

The summary parser reads the event entities in each snapshot. Freestanding
events carry the event in `eType` (`ET_EVENTS + event`), and a temp entity stays
in several snapshots, so the scan mirrors cgame's per-entity `previousEvent`
dedupe. The test demo yields 15 obituaries and final totals `other player 10/5`,
`POV player 4/10`.

The map step shows the resume under the map check: map, time played, the match
clock and a `Player / Score / Deaths / Status` table. Spectators are hidden
unless they have kills or deaths. `Score` is the event kill count.

### Game boundaries and stats reset

A new resume is created on a `svc_gamestate`, a map change, a `map_restart`
server command, or a `CS_LEVEL_START_TIME` change. A command restart opens the
next game immediately; the server's delayed level-start update is merged into
that game instead of creating a short empty resume. Player records, kills,
deaths and the match clock all start again for each game. Internal zero-stat
restart gaps are dropped from the summary.

The test demo `multi-round.dm_26` has one gamestate, two
`map_restart` commands and three resumes: a 3.9 s opening, the 12:15 game with
55 obituaries, and an 8.6 s ending. The 12:15 game starts with kills/deaths at
zero and a reset match clock.

## Follow camera pitch

The followed entity's `lerpAngles` carries the remote player's view yaw **and**
pitch. The third-person follow camera now starts at the model's eye and pulls
back along that view direction, so looking up/down moves the camera vertically
as well as aiming it. Dead players use a level pitch so a corpse's lean does not
throw the camera into the floor. The recorded POV client still uses its real
`predictedPlayerState.viewangles`.

## Exact kills/deaths and vitals at a seek target

The app keeps the parsed event list and, on every scoreboard poll, replays the
events up to `status.serverTime` with `statsAt()` in
`app/src/summary.ts`. `mergeScoreboard()` replaces the cgame's incomplete
event counters and keeps disconnecting players in the side panel with
`left: true` (Follow is disabled for them). This makes the side panel exact
immediately after a seek; the status poll catches up within one tick.

The same poll replays the per-game vitals samples with `vitalsAt()` and adds
each player's health and armor to the scoreboard row. The samples are stored
per game, so a map restart or a new gamestate starts everyone back at the 100/25
spawn defaults. Only kills and deaths are attributed to an attacker; the
vitals timeline records the target, time and remaining health/armor, which is
the raw data needed to derive damage dealt later.

`mergeScoreboard()` also fills the TypeScript HUD's `view` object for the
followed player: `health` and `armor` come from `vitalsAt()`, and `saberStyle`
comes from `stanceAt()` when the cgame reports no remote stance (`-1`). The
recorded POV keeps its exact playerState style. This is what makes the HP/AP
bars and the weapon/stance block show values while following another player.

`damageAt()` replays the damage instances into per-player totals and the full
attacker→target matrix. The scoreboard row shows only attributed `dealt/…
received` totals under `kills/deaths` (the pair is right-aligned in the score
column); the per-opponent matrix stays in the summary for a later breakdown.
Damage that the demo cannot attribute is kept with attacker `-1` and is not
added to either displayed total, so `dealt` and `received` describe player-vs-
player damage only.

## Async engine calls

All long engine operations (`play`, `pause`, `stop`, `seek`, demo info,
asset/map staging and restart) go through a serialized queue in
`EngineHost`. This prevents a second `ccall({ async: true })` from starting
while another Asyncify operation is in flight, which caused
`Aborted(Assertion failed: We cannot start an async operation when one is
already in flight)` on restart/seek.

`playDemo` is also single-flight: a second click while the first map load is
still running joins the same promise instead of queuing another
`JKA_PlayDemo`, and the Watch again/Restart handlers share a guard.

At the end of a demo the Emscripten build now leaves the last frame in place
instead of disconnecting and tearing down the renderer/map. That teardown was
still in flight when Replay started and caused the Asyncify assertion. Replay
starts the demo from a stable frame; Stop still performs the full disconnect.


## Local cache

> **Superseded by M9 Phase 3:** the OPFS asset cache described below was
> removed. The worker host mounts the PK3s read-only with WORKERFS and the
> main-thread fallback stages them into MEMFS for the session. A one-time
> cleanup deletes the old `jka-demo-player/assets` tree. See
> `docs/m9-phase3.md`. The summary cache below is unchanged.

### OPFS assets

After a successful map check the four retail PK3s are copied into OPFS in the
background (`app/src/fs/assetCache.ts`), with a progress line while writing. A
manifest is written last; only complete sets are offered.

On the next load the assets step shows **Use cached assets**. Loading it stages
the PK3s from OPFS, so the folder picker/permission step is skipped. The engine
still copies the files into its MEMFS, so this does not remove the wasm-side
copy; it removes the external source read and makes reloads independent of the
original folder. Measured on the test host: first check map 21.2 s, cached
check map 10.3 s. The cache is about 1.14 GB and can be removed from
**Settings → Local data**.

### Background engine preparation

The engine is created and staged as soon as the assets are validated, while the
user is still on the demo step, instead of waiting for **Check map**. A small
spinner at the bottom of the wizard reports `Preparing the wasm engine…` and
then `Starting the wasm engine…`; if Check map is pressed before it finishes,
the normal progress overlay takes over. Measured check-map time dropped from
about 21 s to 9.8 s with a warm engine.

The engine is deliberately **not** preloaded from cached assets on page load:
staging 1.14 GB before the user has chosen anything caused a memory spike on
low-memory machines. Cached assets are used when the user clicks **Use cached
assets**; the engine then starts immediately from that choice.

### IndexedDB summaries

The parsed summary is stored in IndexedDB under
`jka-demo-player` / `demo-summaries`, keyed by
`v7:name:size:lastModified`. The version prefix invalidates summaries produced
by older game-boundary logic or without the vitals/stance/damage timelines. A
cached summary populates the map step and the timeline without running the demo
scan. The seek keyframes are not persisted (see limitations).

## Playback speed and gamma

The player has a **Speed** slider from `0.25×` to `2.5×` in `0.25` steps. It is
persisted in settings and applies the engine's `timescale` cvar. Measured demo
time over four seconds: `2×` → 8.1 s, `0.5×` → 2.0 s, `1×` → 4.0 s.

Settings also has a **Gamma** slider (0.50–3.00, default 1.00). The engine's
`r_gamma` is applied at boot, so a reload uses the stored value for texture
generation; while the session is running, the same value is applied as a canvas
gamma filter relative to the boot value. That makes the slider immediate
without reloading the map, and avoids double-correcting textures after a map
reload. The speed control is behind a **Speed** button and opens in a small
popover instead of occupying the player bar permanently.

## Indexed seek

During the summary scan the client captures a full keyframe every 10 seconds:

- the reconstructed `clSnapshot_t` (player states, entity count, areamask),
- the snapshot's entity states,
- the current gameState/configstrings,
- the entity baselines,
- the demo file offset of the next message and the server command sequence.

`JKA_SeekDemo` uses these keyframes as jaMME does with its indexed demo player:

- **Forward while playing** — restore the nearest keyframe, resume the file at
  its offset, replay at most 10 seconds and continue. Measured **0.2–0.5 s**.
- **Backward, or after the demo was stopped** — restart the demo, load the map,
  restore the keyframe and replay to the target. Measured **8–12 s**, constant
  regardless of target.
- **No keyframes** — for example when the summary came from IndexedDB after a
  reload, the old replay-from-start path is used. The next scan rebuilds the
  keyframes.

The stock `.dm_26` demo only has four full snapshots, so the keyframes are
full client states reconstructed during the scan rather than file offsets to
full snapshot messages.

## Shader cache

Compiled WebGL programs are not portable and Emscripten does not expose a
persistent shader binary cache that can be saved with the app. The browser's
own GPU shader cache already reuses programs between runs on the same profile.
A parallel shader compile (`KHR_parallel_shader_compile`) could hide some of
the first boot cost without caching, but it is not a trivial change to
rd-rend2's synchronous compile path; this release does not implement it.

## Limitations

- Keyframes are kept in memory for the current page session. A reload with a
  cached summary has no keyframes until the demo is scanned again, so seeks use
  the replay-from-start fallback.
- The warm forward seek keeps cgame initialized from the initial gamestate;
  configstrings for players who joined later may be stale visually. The parsed
  summary still supplies exact stats. Backward/cold seeks restart the demo and
  are safer for mods with many joins.
- `Score` is the event kill count. Objective scores sent by mod-specific server
  commands are not parsed.
- There is no asset cache any more (M9 Phase 3). Older builds could leave about
  1.14 GB in OPFS; the app removes `jka-demo-player/assets` once on startup and
  from **Settings → Local data**. No asset cache is recreated.
- The IndexedDB summary database self-heals when an older database is missing
  its object store; a failed cache read falls back to a fresh scan. The cache
  key includes a summary-format version, so a game-boundary fix forces a
  fresh scan instead of reusing an old one-game summary.
- A very long demo with more than 96 keyframes or a snapshot with more than 256
  entities skips that keyframe and falls back to replay for the uncovered
  range.
