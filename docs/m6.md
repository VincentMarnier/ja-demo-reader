# M6: seeking, model-based follow camera, event scoreboard and vitals

**Status:** Implemented on `master`.
**Scope:** Video-style demo seeking, a first-person follow camera anchored to the
followed player model, pointer-lock mouse look in free cam, an event-backed
scoreboard with deaths, and a custom Health/Armor/saber HUD. Supersedes the M5
follow camera and scoreboard behaviour where noted.

## Features

### Seek timeline

The player now has a timeline under the demo:

- `JKA_DemoInfo(name)` scans the demo once and returns `first` (the first server
  time) and `duration` (last − first, in ms). The scan runs before Play is
  enabled, so the timeline has its full range immediately.
- The range input shows the current position and the total duration, e.g.
  `0:33 / 8:53`.
- Releasing the thumb (or using the arrow/Home/End keys) calls
  `JKA_SeekDemo`, which restarts the demo and reads messages until the absolute
  target server time is reached. The app seeks to `demoInfo.first + position`.
- Seeking reuses the same async `ccall` path as Play, with a **Seeking demo**
  overlay; free cam, follow and the side scoreboard are cleared first.
- Play waits for the duration scan before starting, so playback and seek share
  one consistent time base.

Demos are `.dm_26` recordings, so seeking is replay-based rather than a
keyframe/seek table: the engine fast-forwards from the beginning. On the test
machine a seek to 30 s completes in a few seconds.

### Follow camera uses the player model

M5 placed the follow camera in a third-person offset behind the selected player.
M6 anchors it to the followed entity instead:

- The view origin is the followed player's `cent->lerpOrigin` plus
  `DEFAULT_VIEWHEIGHT`.
- View angles come from `cg.predictedPlayerState.viewangles` when the followed
  client is the demo's recorded POV client. For other players, base JKA
  snapshots carry only the entity, so the model's yaw is used with a level
  pitch.
- The POV client is viewed first-person from its eye. Other followed players
  keep the same eye height but are viewed from 100 units behind the model,
  matching the third-person demo POV. The view weapon is suppressed.

This means the view follows the model rather than the recorded POV client: with
the demo camera the recorded client's view is used, and with **Follow** the
selected player's model position/angles are used.

### Free-cam mouse look

Free cam can now capture the mouse:

- **Capture mouse** calls Pointer Lock on the stage. Relative mouse movement
  becomes yaw/pitch at 0.12°/px; the pitch is clamped to ±89°.
- Pressing Escape or leaving free cam/playback releases the lock; the button
  reflects the current state (`Capture mouse` / `Mouse captured`).
- Arrow-key look and the WASD/Space/Ctrl movement remain available and
  rebindable, so pointer lock is optional.

### Event-backed scoreboard and deaths

The in-game scoreboard is not used as the live source. The side panel is driven
by `JKA_ScoreboardJson`, which combines:

- the server score from the client info (the baseline, updated when the server
  sends scores), and
- kills and deaths accumulated from cgame obituary events.

`CG_Obituary` calls `CG_ExternalTrackDeath(target, attacker)`. Deaths count for
the target and kills for a distinct attacker; spectators are excluded. The
counter is reset in `CG_Init`, so restarts do not carry stats over. The displayed
score is the larger of the server score and the event kill count, which keeps
the panel moving between server score updates and converges when the server
catches up. Each player shows `kills/deaths` in the panel, with the values also
available in the tooltip.

### Custom vitals HUD

The in-game status HUD is disabled and replaced by a React vitals strip above
the timeline:

- followed player (or the local client when nothing is followed) name,
- Health and Armor bars/numbers,
- saber style and saber name when the player has a saber, otherwise the current
  weapon.

`JKA_ScoreboardJson` gained a `view` object with `num`, `name`, `health`,
`armor`, `weapon`, `saber`, `saberStyle` and `saberName`. For the recorded POV
client the full player state supplies health, armor, weapon and saber style.
For any other followed player, base JKA snapshots do not include health, armor
or the current saber style: HP/AP show as `—`, the weapon/saber is read from the
entity state, and duel health is taken from the duel configstring when that
player is an active duelist.

### In-game HUD disabled

The startup cvar block now includes:

| Cvar | Value |
|---|---|
| `cg_externalHud` | `1` |
| `cg_drawScores` | `0` |
| `cg_drawTimer` | `0` |
| `cg_drawRadar` | `0` |
| `cg_drawStatus` | `0` |
| `cg_hudFiles` | `0` |
| `cg_drawCrosshair` | `0` |

The custom score strip, timer, scoreboard and vitals strip replace them. The
portrait/duel status can still be drawn by the game; only the health/armor HUD,
scores, timer, radar, crosshair and external HUD files are disabled. The old
Map/State/Demo-time blocks were removed from the player HUD.

### Match timer

The time between the scores is the map/game clock, not the demo clock:
`levelTime = cg.time - cgs.levelStartTime` (the same value as the in-game
`CG_DrawTimer`). It is returned in `JKA_ScoreboardJson` and polled with the
scoreboard, so a demo that starts mid-match still shows the real match time.

### Loading feedback and scan cache

The map step shows a spinner and "Scanning the demo timeline…" while
`JKA_DemoInfo` reads the demo, and the Play button reads "Preparing timeline…"
until the scan finishes. The result is cached in `localStorage` under
`jka-demo-player.demo-info.v1:<name>:<size>:<lastModified>`, so repeat checks of
the same file enable Play immediately. The engine-boot and map-load modals also
show a spinner next to their title.

## Bridge additions

| Function | Purpose |
|---|---|
| `JKA_DemoInfo` | Scan a demo and return `{"first":ms,"duration":ms}` |
| `JKA_SeekDemo` | Restart a demo and fast-forward to an absolute server time |
| `JKA_ScoreboardJson` | Scores, ping, team, deaths and the `view` vitals block |
| `JKA_FollowClient` | Select/clear the followed player (camera now model-anchored) |
| `JKA_EnableFreeCam` / `JKA_SetFreeCamPose` / `JKA_DisableFreeCam` | Free camera |

The cgame-side implementation lives in `cg_view.c`; the obituary hook is in
`cg_event.c`, the counter reset in `cg_main.c`, and the HUD cvars in
`cg_xcvar.h`/`cg_consolecmds.c` (all applied by
`engine/patches/0004-emscripten-rend2.patch`).

## Limitations

- Seeking replays the demo from the start and does not run cgame frames between
  messages. Obituary events skipped during the fast-forward are therefore not
  counted, so kill/death totals after a seek can lag the server score until the
  next events arrive. The server score remains the baseline.
- Remote demo players do not carry health, armor or current saber style in the
  base JKA protocol. The vitals strip shows those fields only for the recorded
  POV client (plus duel health for active duelists); other followed players show
  their name and known weapon/saber.
- Seek time depends on demo length and machine speed; there is no keyframe
  index yet.
- The first demo scan takes a few seconds on a long demo; later checks of the
  same file hit the `localStorage` cache. Engine shader initialisation can take
  much longer on software WebGL than on a hardware GPU.
- Follow/free cam and the mouse look update while the engine is running. A
  paused engine only redraws after Resume.
- Free cam has no collision detection.
- The external HUD and vitals are demo-player specific; the `rd-vanilla` branch
  keeps the original in-game HUD.
